## Evidenced defects

### A1 — P2: subject report counts unrelated exercise/mistake assets

`backend/api/reports.py:36–57`: `subject` only reaches conversation statistics; mistake/exercise lists omit subject and concept statistics use book only. Probe creates English exercise/mistake then asks `subject=数学`; response says math and counts both as new. The figures and suggestions can mislead the study plan. Fix: use the existing subject hierarchy filter consistently for every report source; define concept exposure scope explicitly. Verification: mixed parent/child/legacy subjects with same book; new/review/practice counters and weak points must match requested cohort, and unknown subject should not leak another cohort.

### A2 — P2: weekly question count loses older turns in an active session

`backend/api/reports.py:105–127`: `_conversation_stats` scans the compatibility JSON `messages` array instead of authoritative SQLite. `backend/conversation_memory.py` bounds that projection to 40 messages. Probe persists 25 user/assistant turns today; authoritative 25 user questions produce **qa_count=20**. Fix: read authoritative paginated/window-by-date storage/query; do not unbound the JSON projection. Verification: >40 messages in the same week, multiple sessions, date/subject/book filtering, empty and legacy-only histories; count 25 and return the latest ten snippets without loading unbounded full history.

### A3 — P3: report day metadata differs from effective range

`backend/api/reports.py:33,81`: calculations clamp days to 1–31 but `range_days` returns original input. Probe `days=100` advertises 100 while cutoff is 31 days. Fix: normalize once and expose the effective range (or reject out-of-range days using request validation). Verification: negative/zero, 1/7/31/100 all have matching metadata and cutoff.

### A4 — P2: direct practice failure commits answer and retry duplicates practice

`backend/api/exercises.py:718–745`: legacy `/practice` calls `bank.record_practice` and commits before resolving/writing optional mistake storage; unlike PracticeAnswerService, it neither isolates failure nor owns a stable operation receipt. Injected mistake-provider `OSError` propagates after persistence. Retrying the same request fails again and **practice_count becomes 2** despite no successful response. Fix: route direct practice through a domain service with a stable attempt operation id/receipt and explicit partial outcome/reconciliation for cross-database writes. Preserve already-recorded answers; do not imply an impossible atomic commit across independent DBs. Verification: mistake-store failure before/after add, link and occurrence; identical retry yields one practice event and eventual single mistake/source/occurrence; changed payload under same operation id conflicts.

A1–A3 were repaired after lead authorization. Report filtering now consistently uses subject hierarchy, explicitly scoped questions require the requested book/subject (unknown scope is not assigned to a precise report), `range_days` matches the clamped cutoff, and the new report helper counts all authoritative cursor pages while retaining only ten question snippets. Nine dedicated regression cases plus the original weekly report and eleven learning-state cases pass. Source and test scope remains local/offline; no database schema, dependency or paid model changes.

A4 remains open. Structured escalation: severity P2; direct practice has no operation id/receipt, while the existing PracticeAnswerService relies on a stable persisted practice-session identity and its stored results. Catching optional write exceptions could disclose a partial outcome, but cannot make retry safe or reconcile a cross-DB occurrence; rollback after the answer commit could destroy a genuine attempt. A complete repair needs a stable direct-attempt request/storage contract and reconciliation verification listed above. No unsafe compensation or feature removal was applied. UI reachability/prioritization should be checked by the main audit.
