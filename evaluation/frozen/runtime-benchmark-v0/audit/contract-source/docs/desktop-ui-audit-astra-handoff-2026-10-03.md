## 已确认的原因与稳定边界

- 笔记生成 prompt 已要求独立可读、避免流水账；当前问题不能仅凭截图归因为“复用了教材生成链路”。`backend/services/session_notes/generation.py` 是有界抽取/组织，正文展示逐块 meta 为确定性原因。提示词可改进文章组织，但不能靠删除来源校验解决。
- `NoteBlocks` 对每个 block 独立调用 Markdown 并追加 `.note-block-meta`，割裂段落/列表/公式间距；需要文档阅读结构及检查模式，而不修改冻结来源。
- `ChatMessage` 的错题按钮显示条件仅 `variant === 'message' && isUser && questionContent.body.trim()`。创建 `/mistakes/drafts` 后跳转录入，没有展示持久关联状态；跨重启准确判断需要核查现有来源字段能力。
- `ApprovedWorkspace.css` 已有阅读宽740、正文16、界面13、元数据11、chrome48等角色。Astra 应先评估批准过的学习/教材基准，再决定需保留哪些、改善哪些，不能以用户反馈为借口回滚到旧页面样式。
- 正式笔记仍须用户主动保存；草稿自动保存不能算正式保存。revision CAS、操作幂等、警告 hash 匹配、后台中断不自动付费重跑、离线阅读保持。
- 来源从正文退场不意味着提升数学验证状态；必要未核实内容有可理解的摘要和可发现详情。
- 选择策略必须分 chrome / readable content / editable content；公式编辑器、选择区复制、输入全选与键盘菜单不可损坏。

## Astra 交付要求

1. 形成统一桌面工作区方案：应用 chrome、集合管理、阅读文档、任务状态、菜单/弹窗、错误恢复的层级和组件职责。
2. 将用户U1–U5与主动A1–A15逐项映射到设计决定、Sol文件范围、验收场景；提出明确优先级与阶段。
3. 给出可直接实现的视觉角色、头部高度/长标题策略、字号/行距/宽度/控件、文档操作及来源检查交互；避免“更好看”“更现代”等不可验收描述。
4. 会话置顶/归档/删除与跨重启错题状态明确区分立即可实现和需要服务/存储设计的工作。若必须架构、迁移、删除用户数据或依赖重装，形成具体可审阅方案后征求用户同意。此轮只可安全实现已有契约上的 UI；不可伪造可用菜单。
5. 小模型整理侧重、Goal持久对话列后续决策，不擅自上线新的模型或Runtime。
6. Sol 至少覆盖1280×820、1024×768、760×820、长中文、公式、混合状态、空/生成/失败/中断/待核实、键盘、选择复制、侧栏收起；Electron优先。说明未能实际验证的平台。跑适用lint、tests、build和desktop checks，记录patch_notes。
